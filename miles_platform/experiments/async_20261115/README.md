# 全异步训练对照实验 — 2026-11-15

在 3 张 A100 上用同一配方对比同步与全异步的 Qwen3-0.6B FSDP GRPO。结论：**全异步每次更新的耗时中位数从 24.7 秒降到 14.7 秒（少 40%），采样策略与训练策略之间的 KL 基本不变；把在飞回答数翻倍没有更快，只让策略滞后从 2.6 个版本升到 3.7 个。** 12 次更新、学习率 1e-6 不足以改变模型，评测准确率只有噪声，所以这里只比较了速度、滞后和数值一致性，没有比较训练质量。

[汇总脚本](summarize.py)、[全部指标与逐次更新序列](results.json)。所有数字都由脚本从 Miles 日志行读出，没有估算。

## 做了什么

参照 Beam 技术报告 4.1.2 与 4.4 节。Miles 上游已有全异步 rollout，但没有 FSDP 后端加全异步的示例或测试；这里把它接到平台配方上并实际跑通：

- `scripts/run_qwen3_0_6b_platform.py --fully-async` 改用 `train_async.py`。常驻的 rollout worker 持续生成，训练器按组取走已完成的回答。
- 每次优化器更新后把权重推给推理引擎（`--update-weights-interval` 默认 1）。在飞请求以 `in_place` 方式保留 KV cache 继续生成，所以一个回答可以跨多个策略版本。
- 每段 token 记录生成它的策略版本，据此得到策略滞后指标。
- 用截断重要性采样（`--use-tis`，上界 2.0）修正滞后。
- 可选：`--max-weight-staleness` 丢弃过旧的组，`--async-max-concurrent-samples` 限制在飞回答数，`--nucleus-top-k` 开启 top-p 0.99 采样。

报告里没有照搬的部分：按任务设定的 rollout 截止时间、judge 模型、MoE 路由回放、LM head 与残差流的 FP32 计算。本配方是单轮数值题和稠密模型，前三项不适用。

## 环境与方法

- Vast 实例，NVIDIA A100-SXM4-40GB × 3（2 张训练，1 张 rollout），PyTorch 2.14.1+cu130、Transformers 5.19.0、Ray 2.58.1、SGLang `18a44326`。
- Qwen/Qwen3-0.6B revision `c1899de289a04d12100db370d81485cdf75e47ca`；`zhuzilin/gsm8k` revision `0cbd9f31d91ac21a7613dcbc7fef992adac459ae`，train 前 512 条训练，test 前 64 条评测。
- 每组 12 次更新，每次 8 个 prompt × 4 个回答，学习率 1e-6，采样温度 1.0，回答上限 512 tokens，平台的数值评分器。五组顺序运行，每组单次，没有重复。
- 每次更新耗时取相邻两条优化器 step 日志的时间差的中位数，不含启动、导出和第一次更新。每次更新后都对 64 条评测集做一次评测，这段时间包含在内。
- 策略滞后是训练器取用样本时，样本最旧 token 的策略版本落后当前版本的个数。

## 结果

| 配置 | 每次更新耗时（秒，中位数，括号内为范围） | 启动器总耗时（秒） | 平均滞后（版本） | 最大滞后 | 跨版本回答占比 | 采样-训练 KL | 丢弃的组 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 同步 | 24.7（21.4–26.0） | 528 | — | — | 0% | 0.00065 | — |
| 全异步 | 14.7（14.3–15.3） | 359 | 2.58 | 4 | 72% | 0.00068 | 0 |
| 全异步，在飞 64 个回答 | 14.8（13.8–15.6） | 351 | 3.71 | 6 | 57% | 0.00078 | 0 |
| 全异步，在飞 64，滞后上限 2 | 14.8（13.7–15.8） | 346 | 1.66 | 2 | 74% | 0.00063 | 21 |
| 全异步，top-p 0.99 / top-k 64 | 15.0（14.7–15.5） | 355 | 2.65 | 4 | 72% | 0.00064 | 0 |

- 全异步每次更新少 40%，整个启动器耗时少 32%（后者包含三四分钟的启动、首次更新与收尾）。
- 默认并发是一个训练批（32 个回答）。翻倍到 64 没有缩短更新耗时，平均滞后却从 2.58 升到 3.71。报告 4.4.2 节有同样的观察：并发超过服务能力后只增加延迟。
- 把滞后上限设为 2 后，平均滞后降到 1.66，代价是丢弃了 21 个 prompt 组（相对于被训练的 96 个组），更新耗时没有变化。
- 同步训练的采样-训练 KL 已有 0.00065，这是训练器与推理引擎之间的数值差异，不是滞后造成的。全异步下它在 0.00063–0.00078 之间，逐 token 对数概率的平均绝对差约 0.013。作为参照，报告的对应数字是 KL 中位数 0.00022 和绝对差 0.0085；两者的模型、精度和采样设置都不同。
- 重要性采样权重被截断的比例不超过 0.005%。
- 五组的评测准确率都在 0.45–0.63 之间波动，没有可辨别的趋势。

## 未验证的事项

- 没有任何关于训练质量的证据。要判断滞后是否伤害学习，需要更大的学习率、更多更新和重复运行。
- GSM8K 回答长度差异不大（平均约 190 tokens，上限 512）。报告里异步的主要动机是时长重尾的 agentic 任务，这里没有复现那种负载，收益主要来自生成与训练、评测的重叠。
- top-p 那组只证明带这些参数的全异步训练可以完整跑完。日志里没有能确认"训练时按记录的 nucleus 重新归一化"确实生效的行，这一点没有验证。
- 平台默认的每次更新 4 个 prompt 的配置只在冒烟中跑通，没有计时对照。
- 只在单机 3 卡上运行，没有测试故障恢复和断点续训。

## 复跑

```bash
C="--num-rollout 12 --rollout-batch-size 8 --num-gpus-per-node 3 --trainer-gpus 2 --numeric-reward"
python scripts/run_qwen3_0_6b_platform.py --model-dir MODELS --data-dir DATA --output-dir runs/sync $C
python scripts/run_qwen3_0_6b_platform.py --model-dir MODELS --data-dir DATA --output-dir runs/async $C --fully-async
python miles_platform/experiments/async_20261115/summarize.py logs/sync.log logs/async.log > results.json
```

其余三组依次加上 `--async-max-concurrent-samples 64`、`--max-weight-staleness 2`、`--nucleus-top-k 64`。运行环境按[部署说明](../../../deployments/platform-smoke/README.md)安装。每组结束时保留一个约 7 GiB 的检查点。
